# ADR 0003: Associated data naming

Date: 2026-11-02 · Status: Accepted

## Context

ADR 0002 makes associated data (AD) required and non-empty for every AEAD
ciphertext and every secretstream chunk. AD is what stops an untrusted box from
handing an app the right kind of ciphertext for the *wrong* thing: another
item's metadata, the thumbnail instead of the original, another user's wrapped
key. That only works if every client builds exactly the same AD for the same
object, so the strings must be fixed before M1 stores any data.

There is also an ordering problem. In doc 01's backup flow the app encrypts the
original, preview, thumbnail and metadata (step 3) **before** uploading (step 4),
and the box returns the item id only at the end (step 5). An id the box assigns
afterwards cannot be bound into ciphertext that already exists.

## Decision

**1. Ids are generated by the client that creates the object.** User, device,
collection and item ids are 16 random bytes, written as 32 lowercase hex
characters. The client sends the id when it creates the object; the box rejects
an id that already exists (`409`, code `id_taken`). The box never invents ids
for these objects.

**2. AD is a UTF-8 string:** `cloudbox/v1/<kind>/<id>/<field>`

| Ciphertext | Encrypted with | AD |
|------------|----------------|----|
| Master key, wrapped by password | KEK (Argon2id) | `cloudbox/v1/user/<userId>/master-key/password` |
| Master key, wrapped by recovery key | Recovery key | `cloudbox/v1/user/<userId>/master-key/recovery` |
| Identity private key (X25519) | Master key | `cloudbox/v1/user/<userId>/identity-key` |
| Dedupe key | Master key | `cloudbox/v1/user/<userId>/dedupe-key` |
| Device name | Master key | `cloudbox/v1/device/<deviceId>/name` |
| Collection key (owner's copy) | Master key | `cloudbox/v1/collection/<collectionId>/key` |
| Collection name | Collection key | `cloudbox/v1/collection/<collectionId>/name` |
| File key | Collection key | `cloudbox/v1/item/<itemId>/file-key` |
| Item metadata | File key | `cloudbox/v1/item/<itemId>/metadata` |
| Original, preview, thumbnail (secretstream) | File key | `cloudbox/v1/item/<itemId>/original` · `/preview` · `/thumb` |

The variant names match the `role` values in doc 05's `item_blobs` table.

**3. Sealed boxes have no AD.** A collection key shared with another member
(`crypto_box_seal`) is sealed as `collectionId (16 bytes) ‖ key (32 bytes)`. The
receiver checks the id matches the collection it asked for before using the key.

**4. `v1` changes only with a format change.** A new version string means old
ciphertexts must be re-encrypted or read with the old rule.

## Alternatives considered

- **Box-assigned ids, bind later:** impossible for blobs encrypted before upload
  without re-encrypting after upload.
- **Per-variant subkeys** (`crypto_kdf_derive_from_key`) instead of AD for
  files: works, but AD is already required by ADR 0002 and keeps one rule for
  everything.
- **Collection id in item AD:** not needed. Moving an item re-wraps its file key
  under the new collection key anyway, and the item's own AD does not change.

## Consequences

- M1 adds `@cloudbox/crypto` helpers that build these strings, so no call site
  writes them by hand, plus vectors for each.
- Doc 04's create endpoints (`POST /v1/items`, `/v1/collections`, `/v1/setup`,
  `/v1/devices/pair`) take a client-generated `id`.
- Doc 05's `items` table needs a `file_key_enc` column (the wrapped file key);
  it is not listed today.
- Id collisions are not a practical risk with 128 random bits, but the box still
  checks uniqueness so a malicious client cannot overwrite another's object.
